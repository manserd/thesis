\chapter{Evaluation}

In this chapter we outline the experiments we ran to evaluate the HI and LW type systems and we discuss our observations. As benchmarks we used satisficing problems from the \kw{International Planning Competition}[IPC], which we retrieved from the Fast Downward benchmarks repository\footnote{\url{https://github.com/aibasel/downward-benchmarks}}. Specifically, we used the same IPC 2011 and 2014 domains that \tcite{tomasz2024} used in their first experiment, except that our suite totalled 380 problems whereas \tcite{tomasz2024} report their total number of problems at 376. We were unable to determine where this difference comes from: assume therefore that when comparing coverage numbers between both works, our numbers are slightly higher by default.

All experiments were run on an AMD Epyc 7742 CPU, with a 3584MiB memory limit and 10 minute time limit per task. Aside from the CPU, this matches \tcite{tomasz2024}'s experimental setup, which was done to keep the coverage numbers somewhat comparable across both works. For this same reason, we also used the \kw{FF} heuristic \pcite{hoffmann2001}, treated all problems as unit-cost problems, and used the same default $\Softmin$ temperature of $\tau=1$ for algorithms that perform biased type or state selection, unless specified otherwise. Finally, for stochastic algorithms, all results represent averages over five runs.

\section{Comparison to Original Work}

We first aimed to establish that our implementation is correct and that it performs similarly to the implementation used by \tcite{tomasz2024}. To do so, we replicated the first experiment performed by \tcite{tomasz2024}, which compares coverage numbers between GBFS, \hgUu (which they refer to as Type-GBFS), and all variants of the new algorithms.

We point out two additional caveats that apply to this comparison in particular, but will also remain relevant for all other results. First, coverage can be affected by hardware differences and noise: this is particularly relevant here, where we are comparing results obtained on different systems. And second, all stochastic algorithms inherently behave differently depending on the configuration of the random number generator, which we were unable to match between the experiments performed by \tcite{tomasz2024} and ours: in both works, the results are averaged across multiple runs, but some difference will remain.

\Cref{tbl:replsum} shows a comparison between the coverage numbers reported by \tcite{tomasz2024} and those obtained by us. Our implementation agrees with \tcite{tomasz2024}'s findings that the configurations that pair the heuristic improvement type system with depth-biased type selection, that is \hiDh and \hiDu, perform by far the best.

Interestingly, the difference between the top two performers and the subsequent entries is far less pronounced in our results as in theirs: while \tcite{tomasz2024} observed their third-best configuration, \hgHu, solving almost 20 fewer problems compared to both works' second-best, \hiDh, our third-best configuration, \hiHh, only covered around eight fewer problems than our second-best.

Notably, we generally observe a more gradual decline in coverage from our best to our ``mediocre'' entries, whereas \tcite{tomasz2024} recorded all their ``mediocre'' performers achieving relatively similar coverages, as is illustrated in \Cref{fig:repltrend}. This is most visible with \hiHu, \hiHh, \lwHh, which all score much higher than expected in our case.

Both works then generally agree again regarding which configurations perform the worst, those being \lwUu, \hiUu, \hgUu, and \gbfs, all of which only perform unbiased type and state selection, or no stochastic exploration at all.

Finally, we want to point to GBFS: since this is a deterministic algorithm, and since both works likely used the exact same implementation for it, we assume that the delta in coverage which we record here is mostly attributable to hardware differences. Assuming, therefore, that our coverage numbers are generally about 5-7 higher than theirs by default, it is notable that we nevertheless measure equal or even worse coverage for some configurations: namely, \hgHu and \hiUu show around the same coverage across both works, and \hgUu is slightly worse in our case.

Both with these outliers, as well as with those configurations that scored higher than expected, it would be interesting to investigate if this primarily occurs in specific domains. Unfortunately, since we do not have access to \tcite{tomasz2024}'s per-domain coverage numbers for all configurations, we cannot do this at this time.

\section{Softmin Temperatures}

Recall that $\Softmin$ has a temperature parameter $\tau>0$. This parameter allows us to control how strongly biased selection strategies prefer lower values: at low $\tau$, the strategy almost always selects the lowest or one of the lowest values, whereas for larger $\tau$, biased selection behaves more and more like uniform selection. Since we can control $\tau$ independently for type selection as well as state selection, going forward, we will use $\tau_\text{types}$ when discussing the former, and $\tau_\text{states}$ for the latter.

In \expbt, we test those algorithms that use biased type selection with different $\tau_\text{types}$ to see if some variants might benefit from more or less aggressive type biasing. Due to the larger number of runs, we separate this experiment into two sub-experiments.

\subsection{\expbtone}

In \expbtone, we only use a subset of the reference suite. We call this the \kw{reduced suite}, and it is identical to the reference suite, except that it removes some domains where \exprepl\ (\Cref{tbl:repldomains1} and \Cref{tbl:repldomains2}) has shown all algorithms consistently reaching almost full coverage or almost no coverage at all. In particular, we omit \texttt{childsnack-sat14-strips}, with an average coverage below 0.06, and we omit all the following domains with average coverages at or above 18.44 (out of 20):

{\small

    \texttt{ged-sat14-strips}&\texttt{hiking-sat14-strips}&\texttt{parcprinter-sat11-strips}
    \\\texttt{pegsol-sat11-strips}&\texttt{scanalyzer-sat11-strips}&\texttt{sokoban-sat11-strips}

}

In this and all subsequent experiments using the reduced suite, when we compare coverage numbers to those measured in \exprepl, we adjust the latter coverages by subtracting the coverages achieved in the omitted domains per each configuration.

\expbtone\ only tests a subset of the algorithms: namely, we exclude all variants that use the \Utss type selection strategy, since this strategy does not use $\Softmin$, and we only include variants that use the \Usss state selection strategy. The latter assumes that the type and state selection strategies affect an algorithm's performance independently of each other: we have no reason to assume this to be true and thus acknowledge this as a potential gap in our methodology.

\subsection{\expbttwo}

The goal of \expbttwo\ is to evaluate the most promising algorithms of \expbtone\ on the full reference suite and with temperatures that reach further into the directions that appeared promising.

In \expbtone, \lwHu and \lwDu achieved higher coverage at reduced temperatures: therefore, in this experiment, we additionally test these variants at even lower temperatures. Also, because this experiment omits the HI variants and tests fewer different temperatures overall, we are now also able to evaluate the \Hsss variants of LW.

As \hgHu only showed an improvement at $\tau_\text{types}=2$ and not beyond, and since there are no other state selection strategies for this algorithm, our only goal for this variant is to see if its coverage on the full reference suite remains better at this increased temperature compared to $\tau_\text{types}=1$.

% First, observe in \Cref{tbl:bttwodomains1} and \Cref{tbl:bttwodomains2} that the domains we omitted in \expbtone\ show the same coverage here as in \exprepl, with only \texttt{ged} showing slightly lower numbers. We can therefore reasonably assume that those variants that we tested on the reduced suite in \expbtone\ would likely produce coverage numbers similar to those we predicted in \Cref{tbl:btonesum} when evaluated on the full reference suite.

\Cref{tbl:bttwosum} shows that \lwHh consistently managed to solve about five to ten more problems than \lwHu, which matches the relative improvement we observed between these variants in \exprepl. Interestingly, the same cannot be said about \lwDu and \lwDh: here, \lwDh gradually loses its lead over \lwDu as $\tau_\text{types}$ decreases, suggesting that when LW aggressively prefers types with maximal depth, the state selection strategy may become less important.

Apart from this oddity, we observe no additional improvements compared to \expbtone\ at more extreme values of $\tau_\text{types}$. This matches our expectations, since $\tau_\text{types}=0.25$ will already select the lowest value most of the time.

\section{\expeps}

So far, all of our experiments (as well as those performed by \tcite{tomasz2024}) used algorithms that introduce type-based exploration by alternating between exploitation and exploration on every expansion. These algorithms therefore spend roughly half of their effort on exploitation and half on exploration. This is not necessarily the optimal balance: in their introduction of $\epsilon$-GBFS, which allows us to tune this balance via the $\epsilon$ parameter, \tcite{valenzano2014} found that it can be beneficial to allocate less time to exploration and more to exploitation.

In \expeps, we aim to test our new type systems under different values of $\epsilon$ to see if this applies here, too. For this, we replace the alternating open list that manages exploration and exploitation in our configurations with an open list that only performs an exploratory expansion with some probability $\epsilon$. Note that when $\epsilon=0.5$, this open list performs identically to the alternating open list if the number of expansions is sufficiently large. The range of values for $\epsilon$ that we test include values below $\epsilon=0.5$, since these were the most effective in \tcite{valenzano2014}'s work, as well as one value above $\epsilon=0.5$ to test if our algorithms could benefit from more exploration.

% Note also that, again due to the large number of runs, this experiment uses the reduced suite. Accordingly, the results we present were artificially increased by 120 under the assumption that the omitted domains would have had the same coverage as in \exprepl.

\Cref{tbl:epssum} shows the results of this experiment. Note that the coverages in the \emph{ALT} column, which repeats the coverages from \exprepl\ (minus the omitted domains), are consistently close to those in the $\epsilon=0.5$ column, which confirms that these algorithms behave like the ones that use an alternating open list when $\epsilon=0.5$.
